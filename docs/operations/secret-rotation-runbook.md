# APIキー・Secrets ローテーション手順

## 目的と権限

本番の秘密情報を漏えい・期限切れ・担当者変更に備えて安全に交換する。値を閲覧・変更できるのは管理者だけとし、運営メンバー・部長・一般会員には共有しない。

- 実施責任者: Non（管理者）
- 技術確認: Codex
- 記録先: Notion「WBS｜開発・リリース管理」と「テスト結果・受入確認ログ」
- 禁止: チャット、メール本文、スクリーンショット、Git、Notionへの秘密値の貼付

## 対象一覧

| 種別 | Sites環境変数 | 発行元 | 影響 |
| --- | --- | --- | --- |
| アプリ認証 | `AUTH_SECRET` | 安全な乱数生成 | 全ログインセッション |
| Square API | `SQUARE_ACCESS_TOKEN` | Square Developer Console | 会員状態同期 |
| Square Webhook | `SQUARE_WEBHOOK_SIGNATURE_KEY` | Square Developer Console | サブスク自動更新 |
| メール送信 | `RESEND_API_KEY` | Resend | 認証コード送信 |
| メールWebhook | `EMAIL_DELIVERY_WEBHOOK_TOKEN` | 利用中の配信基盤 | 認証コード送信 |
| Google Places | `GOOGLE_MAPS_API_KEY` | Google Cloud Console | 店舗情報補完 |
| グルメマップ | `GOURMET_MAP_FEED_URL` | Google Apps Script | 店舗一覧同期 |

`EXPO_PUBLIC_` で始まる値はクライアントへ公開されるため、秘密値を設定しない。

## 通常ローテーション

1. Notionに作業日時・対象キー・実施者を記録する。秘密値は記録しない。
2. 発行元で新しいキーを作成する。旧キーはまだ無効化しない。
3. Sitesの本番環境変数へ新しい値を保存する。
4. 新しいサイトバージョンを公開し、次の確認を行う。
   - `/api/platform/health` がHTTP 200
   - Google Places変更時はレスポンスの `configuration.googleMaps` が `true`（秘密値自体は返さない）
   - ログインと認証コード送信が成功
   - Square同期または署名済みWebhookが成功
   - 対象機能のWorkerエラーが0件
5. 監査ログに想定した操作だけが残っていることを確認する。
6. 発行元で旧キーを無効化する。
7. もう一度ヘルスチェックと対象機能を確認し、Notionを完了へ更新する。

## `AUTH_SECRET` の特別手順

`AUTH_SECRET` を交換すると既存セッションが無効になるため、利用の少ない時間帯に実施する。

1. 事前に「再ログインが必要になる」ことを運営へ告知する。
2. 新しい32バイト以上のランダム値を作成し、Sitesへ保存する。
3. 公開後、管理者と一般会員の2アカウントで再ログインする。
4. 管理画面の権限制御と一般会員のアクセス制御を確認する。

## 緊急ローテーション

漏えいの疑いがある場合は、旧キーを先に無効化する。影響時間より漏えい継続の停止を優先する。

1. 発行元で旧キーを直ちに失効する。
2. Sitesへ新しい値を設定し、再公開する。
3. 管理者ダッシュボードの「監視ログ」とSites Workerログを確認する。
4. Square、Resend、Google Cloudの利用ログから不審なアクセスを確認する。
5. 影響範囲、対応時刻、復旧時刻をNotionへ記録する。秘密値は記録しない。

## ロールバック

- 新キーが使えず旧キーが安全な場合のみ、旧キーへ一時的に戻す。
- 漏えい疑いで失効済みの旧キーは再利用しない。
- ロールバック後も新しいキーを再発行し、原因を解消してから再度交換する。

## 定期確認

- 3か月ごと: キー一覧、所有者、最終交換日、不要キーの有無を確認
- 担当者変更時: 共有範囲を確認し、必要なキーを交換
- 公開前: `.env`、ログ、Git追跡ファイルに秘密値がないことを確認
- 毎回: 秘密値そのものではなく、確認結果と日時だけをNotionへ残す
